# Roadmap: доведение Anker Relocation Lead Pipeline до production-ready демо

## Цель

Сделать проект надёжным демонстрационным сервисом для обработки лидов: форма лендинга и Telegram-бот принимают запросы, лиды не теряются, менеджер получает уведомление, а подключаемые CRM и AI-интеграции работают предсказуемо.

Проект следует публично позиционировать как **demo case study**, пока не будут подключены реальные сервисы, политика конфиденциальности и мониторинг.

## Текущий стек

| Область | Технологии |
|---|---|
| Backend | Go 1.22, стандартная библиотека (`net/http`, `slog`, `encoding/json`) |
| HTTP API | `POST /api/leads`, `GET /healthz`, CORS, собственный in-memory rate limit |
| Очередь | Буферизированный канал Go и один воркер |
| AI-квалификация | OpenRouter API; при ошибке — keyword-based mock/fallback |
| CRM | HubSpot REST API, Google Sheets API через Service Account, CSV как резервное хранилище |
| Уведомления | Telegram Bot API, Slack Incoming Webhook |
| Автоответ | Telegram DM или SMTP (`net/smtp`) |
| Frontend | Статический HTML, CSS и JavaScript без фреймворка |
| Reverse proxy | Nginx |
| Контейнеризация | Docker, Docker Compose |
| Тесты | Стандартный пакет `testing`, unit-тесты Go |

## Как запускать

### Демо в Docker

Требования: Docker Desktop с поддержкой `docker compose`.

```bash
cd lead-pipeline
cp .env.example .env
make up
```

После запуска:

- Лендинг: <http://localhost:8080>
- Health-check API: <http://localhost:8081/healthz>
- Логи конвейера: `make logs`
- Тестовые лиды: `make demo-lead` и `make demo-lead-hot`
- Остановка: `make down`

В демо-режиме API-ключи не нужны: используется mock-квалификатор, CSV в `data/leads.csv` и уведомления в stdout.

### Локальная разработка без Docker

Требования: Go 1.22+.

```bash
cd lead-pipeline/pipeline
go run ./cmd/pipeline
```

Сервис будет доступен на `http://localhost:8081`, а CSV по умолчанию создаётся в `../data/leads.csv`.

Тесты и статический анализ:

```bash
cd lead-pipeline/pipeline
go test ./...
go test -race ./...
go vet ./...
```

> `go vet ./...` проходит без предупреждений. Базовые проверки из этапа 0 уже
> включены в `make check` и CI.

## Принципы реализации

1. Не подтверждать клиенту приём лида, пока он не сохранён в надёжном хранилище.
2. Все внешние вызовы должны иметь timeout, ограниченные повторы и наблюдаемую ошибку в логах/метриках.
3. Фоновая обработка должна быть идемпотентной: повтор одного и того же лида не создаёт дубли в CRM.
4. Согласие, сроки хранения и удаление персональных данных должны быть реализованы до любых заявлений о GDPR compliance.
5. Каждый найденный дефект сначала получает регрессионный тест, затем исправление.

## Этап 1. Починить Telegram intake

**Приоритет: P0 · ориентир: 1 день**

**Статус: завершён (2026-07-19).**

### Проблема

После ответа на вопрос о наличии оффера бот отправляет inline-кнопки с `callback_data` вида `intake:Yes, signed`. Обработчик callback принимает только `claim:` и `spam:`, поэтому кнопка не передаёт ответ в state machine.

### Задачи

- Разделить callback-обработку на manager actions и intake actions либо добавить отдельный `IntakeCallbackHandler`.
- Передавать chat ID и значение кнопки в `tgbot.Bot`, чтобы он обновлял нужную сессию.
- Подтверждать Telegram callback через `answerCallbackQuery` и показывать следующий вопрос.
- Добавить команды `/cancel`, `/restart` и понятную реакцию на неожиданный ввод.
- Добавить TTL для сессий и периодическую очистку незавершённых сессий из памяти.
- Добавить явный шаг согласия на обработку данных до сбора национальности и других персональных данных.

### Тесты

- E2E unit-тест: `Update` с callback `intake:Yes, signed` переводит сессию на следующий шаг.
- Тесты `/start`, `/cancel`, неправильного числа членов семьи и истёкшей сессии.
- Тест, что лид не отправляется без явного согласия.

### Критерий готовности

Пользователь может пройти весь сценарий и кнопками, и текстом; в pipeline отправляется один заполненный лид.

## Этап 2. Гарантировать сохранность и корректное завершение обработки

**Приоритет: P0 · ориентир: 1–2 дня**

**Статус: завершён для demo case study (2026-07-19).**

### Проблемы

- При переполнении канала на каждый лид запускается неограниченная goroutine.
- При SIGTERM воркер сразу прекращает чтение очереди; ожидающие лиды не обрабатываются.
- Уведомления тоже запускаются в goroutine, но не входят в `WaitGroup`.
- CSV хранит историю в виде повторных строк, а строки смены статуса не содержат исходных данных лида.

### Задачи

- Определить модель доставки: для демо достаточно *at-least-once*, для production нужна персистентная очередь (PostgreSQL outbox, Redis Streams, NATS JetStream или SQS).
- До внедрения внешней очереди убрать неограниченный fallback в goroutine: применять ограниченный пул воркеров или возвращать контролируемый `503` после успешного durable-save.
- Реализовать graceful shutdown: перестать принимать HTTP-запросы, закрыть очередь, обработать уже принятые лиды с ограничением по времени, дождаться всех notifier/reply задач.
- Сохранить единый event log или перейти на хранилище с сущностями `leads` и `lead_events`; не использовать пустые CSV-строки как обновление состояния.
- Всегда записывать результат квалификации и изменения статуса в fallback-хранилище, даже если основная CRM доступна.
- Добавить correlation ID/lead ID во все логи каждого шага.

### Тесты

- Тест graceful shutdown с несколькими лидами в очереди.
- Тест лимита очереди и отсутствия неконтролируемого роста goroutine.
- Тест, что CRM-error оставляет в fallback и raw-данные, и квалификацию.

### Критерий готовности

После принятого HTTP `202` лид и его актуальный статус можно восстановить после перезапуска сервиса.

## Этап 3. Привести CRM-интеграции к рабочему контракту

**Приоритет: P0 · ориентир: 2–3 дня**

**Статус: завершён для demo case study (2026-07-19).**

### HubSpot

- Сделать реальную идемпотентность сделки: хранить внешний ID/lead ID в custom property и искать существующую сделку перед созданием.
- Не передавать Telegram username как `hubspot_owner_id`: использовать таблицу соответствий username → числовой HubSpot owner ID либо отдельное пользовательское поле `claimed_by`.
- Явно документировать и проверять обязательные custom properties (`nationality`, source, qualification, lead ID).
- Проверять непустой `id` в успешных ответах API, а не игнорировать ошибку `json.Unmarshal`.
- Добавить тесты HTTP-клиента через `httptest.Server`: создание, повторный upsert, 404, 429, 5xx и смена статуса.

### Google Sheets

- Добавить безопасное монтирование service-account JSON в Docker Compose: Docker secret или read-only bind mount.
- Не хранить путь к ключу как неработающее значение по умолчанию без соответствующего mount.
- Реализовать обновление статуса по `lead_id` либо честно указать, что Sheets — только append-only экспорт.
- Добавить проверку существования заголовков листа и понятную ошибку конфигурации.

### CSV

- Либо оставить CSV только event log с чёткой схемой событий, либо заменить его на SQLite/PostgreSQL для upsert и поиска по `lead_id`.
- Добавить защиту от повреждённой/частично записанной CSV и ротацию файлов.

### Критерий готовности

Повторная доставка одного лида создаёт не более одной сущности в основной CRM, а fallback хранит полную историю независимо от CRM.

## Этап 4. Безопасность и персональные данные

**Приоритет: P0 для публичного доступа · ориентир: 2 дня**

**Статус: завершён для demo case study (2026-07-19).** Реальный публичный запуск по-прежнему требует настроенного HTTPS, процедуры удаления данных и назначенного оператора данных.

### Задачи

- Реализовать отдельную страницу privacy policy и сделать реальные ссылки с лендинга.
- Запрашивать и сохранять явное согласие в обоих каналах; сохранять версию текста, timestamp и источник согласия.
- Определить срок хранения, процесс удаления и контакт для запросов субъекта данных.
- Ограничить CORS в production конкретным доменом; `*` оставить только для локальной разработки.
- Не доверять `X-Forwarded-For` и `X-Real-IP`, если запрос не пришёл от доверенного reverse proxy.
- Нормализовать IP без порта для rate limiter; добавить TTL-очистку ключей, лимит размера map и, при необходимости, Redis rate limit.
- Добавить ограничение размера и длины каждого текстового поля, проверку `Content-Type`, `DisallowUnknownFields` и защиту от повторной отправки формы.
- Хранить API-ключи только в secrets/переменных окружения; исключить ключи и `.env` из репозитория.
- Настроить HTTPS, security headers и ограничение body size в Nginx.

### Критерий готовности

Лендинг не заявляет «GDPR compliant» без реализованных процессов, а API нельзя легко обойти подменой заголовка или созданием тысяч лимитер-ключей.

## Этап 5. Надёжность внешних интеграций

**Приоритет: P1 · ориентир: 1–2 дня**

**Статус: в работе (2026-07-19).** Добавлены bounded retry с context-aware
backoff и jitter для CRM/уведомлений, записи исчерпанных задач в CSV event log,
независимые задачи manager notification и auto-reply, а также TLS/timeout для
SMTP. Остаётся настроить устойчивую идемпотентность отправки уведомлений на
стороне конкретных провайдеров.

### Задачи

- Использовать context-aware backoff вместо `time.Sleep` в уведомлениях.
- Добавить retry policy для CRM и notifier: only transient errors (429/5xx/network), экспоненциальный backoff, jitter и максимальное число попыток.
- Добавить dead-letter/event log для задач, исчерпавших попытки.
- Ввести idempotency key там, где API его поддерживает; иначе обеспечивать её на своей стороне.
- Разделить уведомление менеджеру и автоответ клиенту на независимые задачи с отдельным результатом.
- Настроить таймауты SMTP и безопасный TLS; рассмотреть современный SMTP-клиент вместо устаревшего `net/smtp`.
- Добавить проверку/экранирование пользовательских данных во всех форматах сообщений Telegram и Slack.

### Критерий готовности

Временная ошибка OpenRouter, CRM или Telegram не блокирует сервис и оставляет понятный след для повторной обработки.
